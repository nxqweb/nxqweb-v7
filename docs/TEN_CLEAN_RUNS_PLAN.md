## The traps (all found in the repo or on the page)
1. **DENY runs do not count** (above).
2. **The Netlify build guard.** `nxq_netlify_budget_settings` defaults to `max_builds_per_cycle = 4` and `max_qa_builds_per_cycle = 2` (migration 234). An approve run reserves a preview and a production build (and, until the `stop_builds` fix is proven, a third), so the defaults give about **one approve run per cycle**. The current staging values are not recorded anywhere; read them first. No screen in the app changes them. The owner function `owner_update_netlify_budget_settings(...)` checks `auth.uid()`, which is empty in the Supabase SQL editor, so from there use a plain table update, as was done for the cost cap: first `select * from public.nxq_netlify_budget_settings;`, then (owner's choice of numbers) `update public.nxq_netlify_budget_settings set max_builds_per_cycle = 15, max_qa_builds_per_cycle = 15, updated_at = now() where singleton = true;` (the QA number may not exceed the cycle number). The alternative is a small owner screen that calls the function with the owner's own login (see below).
3. **Netlify credits, and they lag.** Measured on 2026-10-07: a new QA site cost about **45 credits** (Netlify ignored `stop_builds` at site creation, so the site made two production deploys by itself, plus the promotion). The fix expects about 15-30, unproven until a run measures it. Netlify's billing page today carries a banner: "We are experiencing some issues with our billing systems. Credit consumption reporting may be delayed." It read **209.5 of 300** (the cycle runs Oct 23 to Nov 22). A stale reading is how the team ran out on 2026-10-07, so: read before, read again five minutes after each run, and start the next run only when two readings agree.
4. **The platform cost cap.** Staging's `nxq_platform_cost_settings` is `monthly_limit_cents = 500` ($5). QA clients draw every paid job from it (an estimated 30-40 cents per run), and billing and alert emails draw on it too. If a run stalls with a cost-blocked error, check this first; raising it is the owner's decision.

5. **The monthly platform cost pool is drained on the 1st by maintenance of old disposable QA clients (FOUND 2026-11-04, first measured run).** The run `QA-842A688FA6D1` stalled at its third step: `prepare_build_plan` and `provision_project_infrastructure` sat `queued, attempts 0` with "Skipped by billing guard: PLATFORM_COST_BLOCKER: monthly platform cost limit reached" (so no Netlify credits were spent). A read-only query of `nxq_platform_cost_reservations` for November showed **500 reservations, all `qa:technical_maintenance`, 1 cent each = 500 cents, the last at 2026-11-01 00:49 UTC**: the whole $5 cap was used within the first hour of the month. Cause: `nxq_guard_maintenance_transition` (migration 246) reserves 1 cent every time a `website_maintenance_tasks` row for a QA-only client goes to `running`, and the monthly maintenance for the leftover disposable QA clients made 500 attempts at the start of November. It will recur every month. Estimated cost per run is only about 21 cents (prepare_build_plan 10, provisioning 2, safe branch 5, previews and checks 1-2 each). Options: (a) raise `monthly_limit_cents` (estimates only: no paid AI or email provider is connected, so real spend is $0; reversible); (b) stop old disposable QA clients' maintenance (owner row edits); (c) a migration that stops QA maintenance drawing from the pool (gated product decision). Unblocking by (a) is the quick path; (b) or (c) removes the monthly recurrence. **(a) was done by the owner at about 1:53 PM on 2026-11-04 (`monthly_limit_cents` 500 to 2000) and the run RESUMED BY ITSELF within about five minutes** (blocked jobs sit on a 15-minute retry timer, no manual rescue): `prepare_build_plan` completed at 21:58 UTC and `provision_project_infrastructure` started at 21:59 UTC. **(c) is now REAL migration `supabase/migrations/287_qa_maintenance_off_the_cost_pool.sql` (promoted 2026-11-04 on the owner's choice and APPLIED to staging the same day, run #282, dry run #281 listed exactly 287; regression test `scripts/sql/local-full-schema/regression/287_qa_maintenance_off_the_cost_pool.test.sql`)** (QA maintenance reserves 0 cents and a full pool no longer stops it; every other check, such as a stopped QA client, still applies; real clients unchanged; local harness 51/51; planted bugs for "still 1 cent", "pool still blocks" and "swallows every refusal" are each caught). It is applied, so the pool can no longer be drained by QA maintenance; the cap can go back to 500 (owner's choice).
